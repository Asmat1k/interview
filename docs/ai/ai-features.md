# Разработка AI-функций

Использование ассистента при написании кода и встраивание модели в продукт — разные задачи. Во втором случае разработчик проектирует API, обработку данных, пользовательский опыт, ограничения стоимости и проверку качества.

## Базовая архитектура

```text
Браузер → API приложения → авторизация, валидация, лимиты
                        → доступный пользователю контекст → провайдер модели
                        ← проверка ответа, ошибок и завершения
Браузер ← ответ или поток событий
```

Привилегированный ключ провайдера храните на сервере. Значение, встроенное в frontend bundle или переменную окружения, доступную клиентской сборке, не является секретом. Прямое подключение браузера допустимо только по предусмотренной провайдером схеме с ограниченными краткоживущими credentials.

Backend связывает запрос с пользователем, ограничивает размер входа и бюджет, проверяет доступ к источникам и инструментам. Содержимое запроса модели само по себе не является авторизацией.

## Structured output и runtime-валидация

Промпт «верни JSON» не гарантирует валидный JSON. Структурированный вывод с поддерживаемой схемой повышает надёжность формата, но не делает значения достоверными. Обрабатывайте отказ модели, обрыв ответа и несовместимость схемы.

Пример независимой проверки уже полученного ответа, без SDK и сетевого запроса:

```typescript
type Classification = {
  category: "bug" | "question";
  summary: string;
};

function parseClassification(raw: string): Classification {
  const value: unknown = JSON.parse(raw);

  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("Ожидался объект");
  }

  const record = value as Record<string, unknown>;
  if (
    Object.keys(record).length !== 2 ||
    (record.category !== "bug" && record.category !== "question") ||
    typeof record.summary !== "string" ||
    record.summary.trim().length === 0 ||
    record.summary.length > 500
  ) {
    throw new Error("Ответ не соответствует контракту");
  }

  return { category: record.category, summary: record.summary.trim() };
}

console.log(parseClassification('{"category":"bug","summary":"Ошибка поиска"}'));
// parseClassification('{"category":"admin","summary":"..."}'); // ошибка
```

Оба вида ошибок — JSON-синтаксиса и контракта — вызывающий код должен обработать. На больших схемах используйте валидатор схем, принятый в проекте. TypeScript `as Classification` не проверяет внешние данные в runtime. Даже прошедшая валидацию категория может быть семантически ошибочной: это проверяют evals.

## Embeddings и семантический поиск

**Embedding** — числовой вектор представления текста или другого объекта. Близость векторов используют как сигнал сходства, часто через cosine similarity. Близость не доказывает истинность, актуальность или наличие права читать документ.

Для индекса и запроса нужны совместимые embedding-модель и настройки. При смене модели обычно требуется переиндексация. Векторная БД — удобный вариант индекса, но для маленького набора может хватить простого поиска, а для точных идентификаторов полезен полнотекстовый поиск.

## RAG: ответы по внешним знаниям

**Retrieval-Augmented Generation** добавляет к запросу найденные внешние материалы без переобучения весов модели.

```text
Индексация: документы → фрагменты (chunks) + metadata → поисковый индекс
Запрос: пользователь → фильтр прав → поиск → отбор/reranking
                    → контекст с источниками → модель → проверка ответа
```

Семантический поиск можно сочетать с keyword/BM25; reranker повторно оценивает релевантность найденных фрагментов. Размер фрагмента и число результатов подбирают на своих данных. См. [Anthropic — Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval).

В учебном помощнике документации сохраняйте URL, заголовок, версию и дату источника. На запрос «как отменить запрос?» ищите разделы об отмене, затем передавайте фрагменты со ссылками. Если подтверждения нет, система должна сообщить об этом.

Частые ошибки RAG:

- Разрыв определения и примера при нарезке документа.
- Устаревший индекс после обновления или удаления исходника.
- Документ другого tenant попадает в контекст: фильтрация доступа нужна до передачи модели, включая кэш и историю.
- Правильный фрагмент не найден; модель выдумывает ответ.
- Фрагмент найден, но ответ неправильно его интерпретирует или ссылается на несвязанный источник.

Поэтому качество retrieval и качество ответа измеряют отдельно. RAG уменьшает часть проблем с нехваткой знаний, но не устраняет галлюцинации или prompt injection.

## Промпт, RAG или fine-tuning?

| Потребность | С чего начать | Ограничение |
| --- | --- | --- |
| Изменить формат или дать правила | Инструкция, few-shot, schema | Не даёт новых актуальных данных автоматически |
| Отвечать по обновляемой базе с источниками | RAG или прямое добавление небольшого документа | Нужны поиск, актуализация и контроль доступа |
| Устойчивое специальное поведение на многих примерах | Fine-tuning после измерения базового решения | Нужны качественные данные, обучение и регрессионная оценка |
| Получить баланс или выполнить действие сейчас | Инструмент с авторизацией | Нужны проверки и обработка повторов |
| Рассчитать налог по формальным правилам | Проверяемая программная логика | Требует явного описания правил |

Fine-tuning меняет веса; RAG меняет контекст запроса. Эти подходы можно сочетать. Дообучение не является удобной заменой базе актуальных фактов, а большой промпт не всегда заменяет качественный поиск.

## Streaming и frontend UX

Streaming передаёт результат постепенно. Он уменьшает время до видимого начала ответа, но не обязательно время до полного результата.

Для интерфейса нужны состояния: ожидание, генерация, завершение, отмена, частичный ответ, ошибка и отказ. Предусмотрите кнопку остановки и повтор запроса. Один сетевой chunk не равен одному токену или полному JSON-сообщению: разбирайте протокол SDK, SSE или другой выбранный формат с буферизацией.

Отмена через `AbortController` на клиенте должна по возможности передаваться upstream. Разрыв соединения не гарантирует прекращения генерации и списаний у провайдера.

Не выполняйте действия по незавершённому JSON. Для Markdown используйте безопасный renderer. Сообщайте о прогрессе доступным способом, не заставляя screen reader перечитывать каждый токен; сохраняйте клавиатурный фокус и не перехватывайте прокрутку у читающего пользователя.

## Надёжность, стоимость и наблюдаемость

- **Тайм-ауты и отмена:** ограничивайте ожидание и длительность агента.
- **Повторы:** для временных ошибок применяйте ограниченный backoff с jitter и учитывайте `Retry-After`. Запись требует идемпотентности.
- **Лимиты:** квоты пользователя/tenant, параллелизм, входные/выходные токены и число tool calls. Лимит одного запроса не ограничивает месячные расходы.
- **Fallback:** понятная деградация или альтернативная модель с отдельно проверенными возможностями; повтор не должен дублировать действие.
- **Версии:** фиксируйте модель, промпт и конфигурацию, проверяйте обновления на evals и сохраняйте возможность отката.
- **Логи:** request ID, длительность, модель, usage, причина завершения и ошибки; содержимое запросов храните только по установленным правилам с маскированием данных.

Приближённо: стоимость = входные токены × тариф входа + выходные токены × тариф выхода + инструменты/поиск/хранение. Единицы тарифов, кэширование, reasoning-токены и дополнительные услуги проверяют у провайдера. Считайте весь сценарий, включая неуспешные попытки.

Кэширование может уменьшить задержку и расходы, но ключ кэша должен учитывать пользователя/tenant, права, версию данных и конфигурацию. Кэш с чужим ответом — утечка данных.

Перед выпуском используйте [проверки безопасности и evals](safety-and-evaluation.md); после выпуска отслеживайте качество, p95 задержки, ошибки и стоимость успешной задачи.
