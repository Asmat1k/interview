Работа с AI в повседневной разработке

AI помогает читать код, исследовать ошибку, составлять план, писать черновик реализации и тестов. Разработчик отвечает за требования, архитектуру, проверку результата и поведение в production.

Форматы работы​

ФорматДля чего полезенЧто проверить
Автодополнение в редактореКороткие повторяющиеся фрагментыКонтекст, граничные случаи, лишние вызовы
ЧатОбъяснение, сравнение подходов, локальная задачаПолучила ли модель актуальные файлы и версии?
Агент в IDE или CLIИзменение нескольких файлов и запуск командОбласть работы, права, diff, результаты проверок
Ассистент ревьюПоиск возможных проблем в измененииРеальна ли проблема, есть ли воспроизводимый пример?

Например, GitHub Copilot, Cursor и другие IDE-инструменты предлагают разные сочетания этих режимов. Выбирать стоит по рабочему процессу и правилам организации; одинаковое название режима не означает одинаковые права или возможности.

Рабочий цикл: задача → контекст → план → изменение → проверка​

1. Определить ожидаемое поведение​

Сначала сформулируйте проблему без привязки к коду: кто выполняет действие, какой результат ожидается, что происходит сейчас, какие ограничения важны. Зафиксируйте критерии приёмки. Если задача непонятна человеку, делегирование не сделает её определённее.

2. Передать релевантный контекст​

Укажите версии стека, точку входа, связанные типы, контракт API, существующие соглашения и команду проверки. Для ошибки приложите обезличенный stack trace и шаги воспроизведения. Большой репозиторий сначала исследуют поиском, затем читают нужные файлы.

Prompt engineering — формулировка запроса. Context engineering — управление всем доступным модели контекстом, включая историю, файлы, инструкции и инструменты. См. Anthropic — Effective context engineering.

Файлы правил проекта, например AGENTS.md или аналог в конкретном инструменте, полезны для команд проверки, структуры проекта и соглашений. Их автоматическое чтение и область действия зависят от инструмента. Они не должны содержать секреты и не заменяют технические ограничения доступа.

3. Проверить план​

Для небольшой функции достаточно короткого описания. Для миграции или изменения нескольких модулей попросите перечислить затронутые контракты, риски и способ проверки. Сначала исправьте неверные предположения: иначе быстро появится много кода для неправильной задачи.

4. Внести небольшое изменение​

Задайте границы: какие файлы можно менять, допустимы ли зависимости и изменение публичного API. Проверяйте diff после завершённого шага. Отдельная ветка или worktree упрощают изоляцию; они сами по себе не ограничивают сеть и доступ к секретам.

5. Подтвердить результат​

Читайте код и запускайте необходимые проверки: типы, линтер, тесты, сборку, ручной сценарий. Проверка должна подтверждать требования, а не только совпадение с реализацией. Попросите перечислить выполненные команды, их результаты и оставшиеся ограничения.

Пример хорошего запроса​

Задача: исправить поиск пользователей. При быстром вводе старый ответ API
иногда заменяет результаты для нового запроса.

Контекст: React + TypeScript. Прочитай UserSearch.tsx, api/users.ts
и связанные тесты. Используй версии зависимостей из package.json.
API: GET /api/users?q=... возвращает массив User.

Критерии:
- показываются результаты только для актуального запроса;
- очистка поля сбрасывает результаты;
- отмена запроса не показывается как ошибка;
- настоящая ошибка сети отображается пользователю;
- после unmount запрос отменяется.

Сначала опиши причину и короткий план. Затем внеси минимальное изменение
без новых зависимостей и изменения публичных props.
Добавь проверку гонки ответов и объясни, какие проверки запускались.

Запрос задаёт наблюдаемое поведение и область изменения. Даже после него нужно проверить, что клиент действительно передаёт AbortSignal, обработка отмены соответствует используемой библиотеке, а старый ответ не обновляет состояние.

Zero-shot, few-shot и декомпозиция​

  • Zero-shot: инструкция без примеров. Подходит для понятной задачи с явным контрактом.
  • Few-shot: несколько примеров нужного поведения или формата. Включайте не только счастливый путь, но и пограничные случаи.
  • Декомпозиция: разделение задачи на части с проверяемым результатом: исследовать контракт, исправить функцию, добавить тест, проверить интеграцию.

Пример формата: «Для каждого замечания верни файл, строку, сценарий ошибки и способ воспроизведения. Если доказательств нет, обозначь предположение». Это делает замечания пригодными для проверки.

Просите краткое обоснование, альтернативы и проверяемые свидетельства. Длинный рассказ о рассуждениях модели не является доказательством правильности.

Как применять AI на разных этапах​

ЭтапПолезное поручениеПроверка разработчика
Знакомство с проектомНайти путь данных от страницы до APIОткрыть указанные файлы, проверить реальный вызов
ПроектированиеСравнить два решения по заданным ограничениямУточнить нагрузку, совместимость и стоимость сопровождения
РеализацияНаписать ограниченный фрагмент по контрактуПрочитать diff, проверить ошибки и сложность
DebuggingПредложить гипотезы и минимальное воспроизведениеПроверять гипотезы по одной, сохранять факты
ТестированиеСоставить матрицу входов и отказовУбедиться, что ожидания выведены из требований
РефакторингИзменить структуру с сохранением поведенияПроверить публичный API и характерные сценарии
ДокументацияПодготовить описание по коду и командамСверить команды, примеры и ограничения

Для frontend отдельно проверьте доступность, клавиатурное управление, состояния загрузки/ошибки/пустого результата, гонки запросов, подписки и очистку эффектов. AI может предложить визуально убедительный компонент с неправильным жизненным циклом.

Полезные соседние темы: асинхронность, состояние React, система типов, сборка и линтеры.

Если модель зациклилась или ошибается​

  1. Сохраните воспроизведение и точный текст ошибки.
  2. Проверьте исходную гипотезу по логам и коду, а не по уверенности ответа.
  3. Уберите устаревший контекст, дайте минимальный пример и актуальный контракт.
  4. Ограничьте следующий шаг: одно предположение, одна правка, одна проверка.
  5. Если прогресса нет, решите часть задачи вручную или смените подход. Смена модели не исправляет неверные требования.

Не принимайте удаление теста, отключение линтера, any, @ts-ignore или проглатывание исключения как исправление причины без отдельного обоснования. Если тест неверен, сначала объясните расхождение с контрактом.

Как сохранить навыки и измерить пользу​

После принятия изменения объясните его без подсказки: входы, выходы, инварианты, ошибки и компромиссы. Для обучения сначала попробуйте решить задачу самостоятельно, затем используйте подсказку и воспроизведите решение без чата.

Измеряйте время до проверенного результата с учётом ревью и переделок, дефекты после выпуска и стоимость инструментов. Число сгенерированных строк, принятых подсказок или написанных промптов не измеряет ценность. Сравнивайте похожие задачи и отмечайте влияние сложности и опыта разработчика.
